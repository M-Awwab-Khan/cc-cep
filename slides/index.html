The problem

A promise, an allowance, and a test that spends it.

  • Chaos engineering: break things on purpose to find weaknesses before users do.
  • SLO: a measurable promise, e.g. 99% of requests succeed.
  • Error budget: the failures that promise allows. At 99%, 1 in 100.
  • Test too hard and you spend the budget. Too gently and you learn nothing.

Question: how hard can we test inside the share we were given?

What we asked

Four falsifiable questions.

RQ1

Does feedback reduce overshoot?

Versus static, threshold-stop and calibrated open-loop, at equal workload, allocation and guards.

RQ2

Does attribution help?

Under known background errors, is comparing with a control copy more accurate than counting everything?

RQ3

Safety vs useful testing?

Stopping at once is safe but teaches nothing. What do we keep in exposure?

RQ4 · partly open

Telemetry lag, load, two SLOs?

Load tested at two levels. Delayed telemetry and dual-SLO interaction were not tested in the cluster.

A negative or inconclusive answer is valid evidence. We pre-registered this.

Our idea

Two copies of the app. One gets the fault.

Usersk6 load
Control copybusiness as usual
Test copyIstio injects delay / abort
Controllerbudget · attribution · intensity

Same traffic, same app. Test minus control = damage we caused, not background noise.

Matched-cohort design. Both copies get comparable traffic; only the test copy gets Istio faults. The difference estimates the harm we caused. Caveat to mention: this is valid only if the copies are isolated, and shared dependencies can contaminate the control.
Accounting

Two promises. Two separate ledgers.

Availability SLO

99% of requests succeed

Allowed bad fraction q = 1%. A failed request is bad.

Latency SLO

95% finish within 500 ms

Allowed bad fraction q = 5%. Slow or failed is bad.

  • Delay fault → spends latency budget only. Abort (HTTP 503) → spends both.
  • Ledgers are never added together, and we count requests over a threshold, not p99 milliseconds.
  • The experiment gets a frozen share A at admission. Example: 60,000 requests × 1% = 600 bad allowed; the experiment gets part.
Stress that a latency error budget counts requests above a threshold. Percentiles like p95/p99 are only supporting metrics. An abort counts against both ledgers because a failed request is also too slow under our conservative definition.
Standing on prior art

What exists, and what we don't claim.

Netflix · ChAP

Baseline vs canary

Automated platform: baseline and canary clusters get small slices of real traffic. Failures or latency go into the canary only, outcomes are compared, and safety mechanisms stop the experiment.

Google · SRE workbook

Burn-rate alerting

Burn rate = observed bad fraction ÷ allowed fraction. Alert on a long and a short window together so real problems fire and blips don't.

Safety rails

Guards every policy shares.

  • Total service budget: service bad + reserve reaches its whole budget
  • Severe burn: total burn ≥ 20×
  • Allocation guard: debit + reserve ≥ allocation
  • Duration: 300 s fault window ends
  • Stale telemetry: older than 5 s stops the run
Reserve R = traffic cap × 15 s675 requests at 32 req/s · 1,350 at 64 req/s. Covers the delay between "stop" and "fault really gone".

Plus operational rules

Disposable cluster only, never production or all namespaces · finite fault · minimum traffic · independent cleanup · emergency-stop file.

All policies share these guards so the comparison isolates how each chooses intensity. We do not promise an absolute budget bound; telemetry delay and removal time create unavoidable overshoot, which we measure.
We found our own bug

Version 1 charged for failures that never happened.

Healthy traffic: 0 failures in 200 requests per interval.

  • Wilson gives a range for a rate. 0 of 200 failed still allows a rate up to ~1.9%.
  • v1 charged 200 × 1.9% ≈ 3.77 requests every interval.
  • 8 healthy intervals ≈ 30 requests: stop boundary hit with zero real failures.
  • Uncertainty is what we don't know. v1 spent it like real damage.
Explain in plain words: Wilson is an honest range for a rate measured from limited data. The mistake was adding that range into the spending every two seconds. This was an algorithmic error, found in the 3 November review and documented in docs/ACCOUNTING-V2.md.
The fix

Version 2: like a bank account.

1

Charge what you see

Debit = bad requests actually observed in the test copy. Zero seen → exactly zero charged.

2

Never refund

Debit is a running high-water mark. A later guess cannot give spent budget back.

3

Optional credit

Subtract a cautious lower bound on failures that would have happened anyway, from the control copy.

D = max over time of max(0, B_treatment − credit)Uncertainty widths are never consumption increments. Debit never exceeds observed treatment bad events.

Credit is off by default and valid only if background failures are independent, identical and uncontaminated. Not valid for shared incidents or drift.

Healthy regression test: 300 observations, exactly zero debit. A cleanup failure is also sticky: later recovery cannot turn a failed run into a successful one. The credit uses a confidence sequence (prior art: Howard et al., 2021); we do not claim a new statistical method.

Open-loop, worked example

One division, done once.

u = usable allowance ÷ ( requests in fault window × bad requests per faulted request )

Abort fault at 32 requests/s

Step 1

480

Usable allowance = A − R = 1,155 − 675 bad requests we may cause.

Step 2

9,600

Requests in 300 s window = 32 × 300.

Step 3

1.122

Pilot measured: each faulted request costs ~1.122 bad requests.

Result

4.46%

480 ÷ (9,600 × 1.122). Held constant for the run.

Check: 4.46% × 300 s = 13.4 fraction-seconds, which matches the measured 13.42. If the pilot cost is wrong, it over- or under-spends.

Click through the four steps. The measured open-loop exposure in the study at 32 req/s on aborts was 13.42, so the arithmetic matches. Its weakness is dependence on pilot calibration.
Closed-loop, short vs long window

Two memories, one decision.

short window · last 5 s (fast, jumpy)long window · last 30 s (steady, slow)
HALVE u if ρ > 1 or (short β > 2 and long β > 2)burn β = (bad ÷ n) ÷ q · risk ρ = D/t_elapsed × t_remaining ÷ (A − D − R)
RAISE u by 0.5 pt if ρ < 0.5 and both β < 1Needs both windows to agree: a real, current problem, not a blip.
The windows slide along the timeline. Requiring both short and long burn to exceed 2× before halving is the same multiwindow idea as Google's SRE alerting. Risk asks: at the current spend rate, will the usable allowance run out before the window ends?
How we score

Two numbers: safety and usefulness.

Safety

Usable-guard overshoot

max(0, D − (A − R))

How many requests beyond the usable allowance the experiment spent. Lower is safer. Full-allocation overshoot was zero for every run, so it cannot tell policies apart.

Usefulness

Exposure, in fraction-seconds

exposure = ∫ u(t) dt

Fault fraction × seconds it was active. Higher means more testing.

10% × 300 s = 30 (max) · 5% × 100 s = 5

Stopping immediately is perfectly safe and perfectly useless. We need both.

Fraction-seconds captures both how hard and how long we tested. The maximum possible is 30 because the cap is 10% over 300 s.

Diagnosis

Why did closed-loop use only 30% on aborts?

Abort · 99% SLO · burn = 100 × fault fraction

spent ≈ 30% of usable allowance (142 of 480)

Delay · 95% SLO · burn = 20 × fault fraction

spent ≈ 93% (447 of 480)

  • Halves when burn > 2, raises only when burn < 1.
  • With q = 1%, a 2% abort fault already burns at 2×. Intensity got pinned to ~0.5–2% no matter how much budget remained.
  • SRE burn gates detect unplanned consumption. A chaos experiment means to burn budget.

So we asked: what if the gates were relative to the experiment's own plan?

This is the key insight from reading the traces after the main study. It motivated the paced follow-up. The stricter the SLO, the more conservative burn-rate gating makes the controller.

Follow-up · 15 November

Budget-paced policy: spend it on purpose.

pace π = r ÷ [ (A − D − R) / t_remaining ]r = observed bad requests per second. Denominator = rate that spends the usable allowance exactly on time.
  • Halve if any ρ > 1, or (short π > 2 and long π > 1)
  • Raise 0.5 pt only if all ρ < 0.9 and both π < 1
  • No usable allowance left → halve

Honest design notes

  • Designed after seeing v7 results
  • 20 runs, collected ~1 week later
  • Paired with v7 by block ID only. Not pooled, not jointly randomised
  • Original closed-loop unchanged, so v7 still replays

In simple words: same loop, but judge spending against the pace that would use the allowance exactly on time, not against the SLO's own limit.

Simple words: "same loop, but we judge spending against the pace that would use up the remaining allowance exactly on time, not against the SLO's own limit." Stress the post-hoc nature before showing numbers.

Limits and next steps

What we do not claim.

Limits
  • One shared node; load via port-forward
  • Five blocks; intervals descriptive, no multiplicity adjustment
  • Synthetic, independent background errors
  • Delayed-telemetry and single-SLO ablations not run; no dual-SLO interaction
  • Paced is post-hoc and time-separated
Next
  • Jointly randomised paced vs closed-loop vs open-loop
  • Real correlated background incidents; contamination tests
  • Telemetry-delay ablations; more services and fault types
  • Distributed leader lease for the controller
